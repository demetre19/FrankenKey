# FrankenKey IME wedge in Chrome WebView textarea — 2026-10-09

## Symptom

While using Herdr Mobile PWA (Chrome-for-Android WebView, `textarea` with
`bind:value`), FrankenKey's keyboard panel hides and never re-shows after
specific field-state transitions. Other keyboards (Gboard) recover on the next
tap; FrankenKey stays wedged until an input event is *delivered* to the field —
pressing Enter (a real `insertLineBreak` commit) or pasting re-arms it.
Tapping the field alone does not.

## Confirmed trigger sequence

Two wedges observed on-device:

1. **Attribute toggle wedge (fixed app-side, keeps FrankenKey implication):**
   the web app used to set `readonly` + `inputmode="none"` on the textarea
   while Web Speech dictation ran, then cleared both on stop. After the
   attributes cleared, the field was editable again but FrankenKey's panel
   never returned — the IME session was not re-established on tap.
   Gboard reshowed immediately.

2. **Residual wedge (FrankenKey-side):** even on a bundle with the attribute
   swap removed entirely, after "mic on → dictate → mic off → Send",
   FrankenKey's panel did not come back. Pressing the Enter key (FrankenKey's
   own hardware/gesture path) delivered an input event and the keyboard
   reappeared. Paste also re-armed it in an earlier session.

## Working theory

FrankenKey does not reshow its input view when a WebView re-publishes an
editable `EditorInfo` without a real input commit — i.e. `onStartInput` /
`onStartInputView` / `onEvaluateInputViewShown` paths treat a restored
editable field as a no-op if the `EditorInfo` is otherwise identical, and
`onFinishInputView` left `inputViewShown=false` permanently. Other IMEs
(Gboard) re-evaluate and reshow on the same callback sequence.

Relevant lifecycle surface to audit:

- `onStartInput(EditorInfo, boolean restarting)` — is the "attribute cleared,
  same field" case reaching it at all, or does Chrome skip restart?
- `onEvaluateInputViewShown()` — does it return false forever after a
  `readonly`/`inputmode` flip even when the field is editable again?
- `onUpdateInputViewShown` / `requestShowSelf` usage — is the reshow request
  ever issued when `EditorInfo.inputType`/`imeOptions` transition back?
- FrankenKey's own voice layer (SpeechRecognizer + EXTRA_ENABLE_FORMATTING)
  holds a parallel session over the same field — check it doesn't keep an
  `EditorInfo` snapshot that suppresses reshow.

## Update — post-fix observations (same evening)

The PWA removed the `readonly`/`inputmode=none` swap entirely (bundle
`1.0.16-387-c5a538b4…`). Result: **mostly fixed, but the wedge still fires
intermittently.** Behavior seen across several dictation→send cycles:

- Sometimes the keyboard reshows on Send cleanly.
- Sometimes it stays hidden until Enter or paste delivers an input event.
- The wedge is **timing-dependent**, not deterministic — a race between the
  recognizer's session teardown (which fires `onEndOfSpeech`/`onFinishInput`
  signals into the same IME connection) and the app's focus/Send sequence.

Revised theory: FrankenKey's reshow path correctly handles a clean
editable-transition but loses a race when an input-method visibility request
lands while a speech session is still finishing — the `inputViewShown=false`
state persists because no later event re-evaluates it. Audit points stand,
plus:

- Any `onFinishInput`/`onFinishInputView` path that runs *after* the field is
  editable again can leave the panel latched hidden. Log `isInputViewShown()`
  at `onStartInputView` entry vs. when the wedged state is observed.
- Check `voiceSession`/`speechRecognizer` teardown ordering vs.
  `onEvaluateInputViewShown` — if teardown posts a delayed hide after reshow
  was requested, it wins the race.

## Fix direction

In FrankenKey's input-view visibility logic: when `onStartInput` fires (or
`onEvaluateInputViewShown` is re-queried) for a field transitioning back to
editable, issue `requestShowSelf(0)` rather than relying on the user's next
keystroke. Cheap guard: on `onStartInputView`, if `isInputViewShown() ==
false && editorInfo.inputType != TYPE_NULL`, force-show. Add a watchdog: if
an input connection is active and editable and `inputViewShown` has been
false for >N ms without an explicit user dismissal, re-request show. Verify
no double-show regression on normal field focus.
